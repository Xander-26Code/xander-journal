# Python 并发与并行：线程、进程和 asyncio 该怎么选？

假设你要处理三个任务：每个任务先向远程服务发出请求，再等待一秒拿到结果。如果严格按顺序执行，总耗时大约三秒；如果让等待时间重叠，总耗时就有机会接近一秒。

这并不意味着你的 CPU 突然快了三倍。程序只是没有把时间全部浪费在等待上。

理解这一点，是区分并发与并行、选择 Python 并发工具的起点。本文先解释概念，再用三个独立可运行的示例，分别演示线程池、`asyncio` 和进程池。所有示例只依赖 Python 标准库。

## 1. 并发关注任务推进，并行关注同时执行

**并发（Concurrency）指多个任务的执行过程在时间上重叠：一个任务尚未结束，另一个任务也已经开始推进。** 它们可以交替执行，也可以在不同计算资源上同时执行。

**并行（Parallelism）强调同一时刻确实有多个任务在执行。** 讨论 CPU 计算时，通常意味着利用多个核心同时做计算。

下面只看两个任务的计算片段，字母代表正在执行的片段：

```text
时间向右 →

串行：先完成 A，再执行 B
核心 1：A A A B B B

单核上的并发：A、B 交替推进
核心 1：A B A B A B

多核上的并行：A、B 同时计算
核心 1：A A A
核心 2：B B B
```

因此，不能把并发简单定义成“假的并行”。并发程序也可以并行执行；只是在单核交替执行时，没有发生 CPU 计算上的并行。

一个厨房里的厨师，在烧水时切菜，是利用等待时间推进多个任务；两位厨师分别在两个灶台炒菜，则可以同时工作。前一种方式已经能缩短做饭时间，不必等到“增加一个厨师”才有价值。

## 2. 先判断瓶颈：等待多，还是计算多？

选择工具前，先观察任务主要在做什么。

| 任务类型 | 时间主要花在哪里 | 常见例子 | 初步考虑 |
| --- | --- | --- | --- |
| I/O 密集型 | 等待网络、磁盘或外部服务 | 接口请求、数据库访问、文件读写 | 线程或异步 I/O |
| CPU 密集型 | 持续执行计算 | 纯 Python 大循环、搜索、组合计算 | 多进程或能利用多核的计算库 |
| 混合型 | 等待和计算都有 | 下载数据后清洗、计算、写入 | 分阶段测量，再选择方案 |

这张表只是起点。例如图片处理虽然偏计算，但底层库可能释放 GIL 或自行使用多线程；文件读取也可能受磁盘带宽限制，增加并发未必更快。

**工具的选择取决于实际瓶颈，而不是任务名字。** 如果慢在数据库的单条查询上，盲目增加客户端线程可能只是让数据库更忙。

## 3. 进程、线程和协程分别是什么？

### 进程：程序运行的资源边界

一个运行中的 Python 程序通常对应一个进程。不同进程有相对独立的地址空间；跨进程传递结果，通常需要队列、管道、序列化或显式共享内存。

可以把进程理解成不同的工作间：各自有自己的桌面和物品，需要交换材料时，要使用约定的通道。

### 线程：进程内部的执行单元

一个进程可以有多个线程。普通 Python 脚本通常从主线程开始，额外创建的工作线程可以执行其他任务。

```text
Python 进程
├── 主线程：组织任务、收集结果
├── 工作线程 1：执行任务 A
└── 工作线程 2：执行任务 B
```

同一进程内的线程共享内存，传递对象方便，但同时修改共享数据时也需要协调。关于线程模型和共享状态，可参阅 [官方 `threading` 文档](https://docs.python.org/3/library/threading.html)。

### 协程：能够暂停和恢复的执行过程

在 `asyncio` 中，`async def` 定义协程函数；调用它会得到协程对象。通常由事件循环驱动任务，在等待异步操作时切换到其他任务。

一个事件循环通常运行在一个线程中：

```text
一个线程中的事件循环
├── 任务 A：等待网络结果，暂停
├── 任务 B：继续执行，随后等待
└── 任务 C：获得执行机会
```

协程并不是“更小的 CPU 核心”。在同一个事件循环线程内，一段协程代码持续占用 CPU 时，其他任务就无法在这个线程里继续执行。

## 4. GIL 限制了什么？

常见的说法是：“Python 有 GIL，所以多线程没有用。”这句话忽略了适用范围。

**在启用 GIL 的常规 CPython 中，同一解释器里的多个线程通常不能同时执行 Python 字节码。** 对主要由纯 Python 运算组成的 CPU 密集型任务，多线程往往不能带来预期的多核加速。

但线程仍然适合很多 I/O 场景：一个线程等待网络或其他阻塞 I/O 时，其他线程可以获得执行机会。一些 C 扩展也会在耗时计算中释放 GIL。相关边界见 [官方 GIL 与性能说明](https://docs.python.org/3/library/threading.html#gil-and-performance-considerations)。

还需要注意版本和构建方式：Python 3.13 起提供可选的 free-threaded CPython 构建，可以在禁用 GIL 时让线程并行执行 Python 代码。这不意味着所有 Python 安装都默认关闭了 GIL；第三方扩展的兼容性也可能影响运行状态。具体说明见 [官方自由线程指南](https://docs.python.org/3/howto/free-threading-python.html)。

所以下文把“启用 GIL 的常规 CPython”作为选型前提。遇到其他构建或大量原生扩展计算时，需要重新测量，而不能机械套用结论。

## 5. 实验一：线程池让等待时间重叠

把下面代码保存为 `thread_demo.py` 后执行。这里用 `time.sleep(1)` 模拟一次阻塞等待，不需要访问真实网站：

```python
from concurrent.futures import ThreadPoolExecutor
from time import perf_counter, sleep


def fetch_item(item_id):
    sleep(1)  # 模拟等待外部服务；不是 CPU 计算
    return f"结果 {item_id}"


def main():
    item_ids = [1, 2, 3]

    start = perf_counter()
    serial_results = [fetch_item(i) for i in item_ids]
    print("串行结果：", serial_results)
    print(f"串行耗时：{perf_counter() - start:.2f} 秒")

    start = perf_counter()
    with ThreadPoolExecutor(max_workers=3) as executor:
        concurrent_results = list(executor.map(fetch_item, item_ids))
    print("线程池结果：", concurrent_results)
    print(f"线程池耗时：{perf_counter() - start:.2f} 秒")


if __name__ == "__main__":
    main()
```

在系统负载较低时，通常能观察到类似结果：

```text
串行结果： ['结果 1', '结果 2', '结果 3']
串行耗时：3.00 秒
线程池结果： ['结果 1', '结果 2', '结果 3']
线程池耗时：1.00 秒
```

耗时只是预期量级，不是每台机器都会得到的精确值。这个实验说明的是等待可以重叠，不能用来证明 Python 计算获得了三倍加速。

代码中有三个关键点：

- `max_workers=3` 限制最多三个工作线程，并不是“有多少任务就创建多少线程”。
- `executor.map()` 返回的结果按输入顺序排列；输出顺序不能证明任务按这个顺序完成。
- `with` 会在退出时关闭执行器，并默认等待已提交任务结束；消费结果时也会暴露任务中的异常。

这些接口行为见 [官方 `concurrent.futures` 文档](https://docs.python.org/3/library/concurrent.futures.html)。

实际请求接口时，除了控制线程数，还要设置请求超时，处理失败，并遵守服务端的限流要求。线程池解决的是任务调度，不会自动替你处理这些业务条件。

## 6. 实验二：asyncio 用一个线程组织多个等待

如果依赖库提供异步接口，可以使用 `asyncio`。保存为 `async_demo.py`：

```python
import asyncio
from time import perf_counter


async def fetch_item(item_id):
    await asyncio.sleep(1)  # 模拟可让出执行机会的异步等待
    return f"结果 {item_id}"


async def main():
    start = perf_counter()
    results = await asyncio.gather(
        fetch_item(1),
        fetch_item(2),
        fetch_item(3),
    )
    print("异步结果：", results)
    print(f"异步耗时：{perf_counter() - start:.2f} 秒")


if __name__ == "__main__":
    asyncio.run(main())
```

通常也会在约一秒后得到三个结果。

`asyncio.gather()` 将多个协程组织为并发执行的任务，并按传入顺序汇总结果；`asyncio.run()` 则负责运行顶层协程。这个脚本写法适用于没有正在运行的事件循环的普通入口。相关行为见 [官方协程与任务文档](https://docs.python.org/3/library/asyncio-task.html)。

### 写了 `async`，就会自动并发吗？

不会。下面这段如果放在协程函数中，仍然逐个等待任务完成，总耗时约三秒：

```python
# 片段：放在 async def 定义的函数内
for item_id in [1, 2, 3]:
    result = await fetch_item(item_id)
    print(result)
```

它没有提前调度多个任务。`await` 表示等待某个可等待对象，在操作需要挂起时可以让出执行机会；它不是“自动并发执行后续代码”的开关。

另外，下面是一个应避免的写法：

```python
# 错误用法示例：定义为异步函数，内部却执行阻塞等待
import time


async def bad_fetch():
    time.sleep(1)
```

`time.sleep()` 会阻塞当前线程。在事件循环线程里调用它，会让其他协程一起停下来。换成真实业务也是一样：同步请求库不会因为放进 `async def` 就变成异步库。

对暂时不能替换的阻塞 I/O 函数，可以考虑 `await asyncio.to_thread(阻塞函数, 参数)`；这会把工作交给线程执行，仍然需要理解线程的成本和限制。不要把它当成纯 Python CPU 计算的通用加速方案。

## 7. 实验三：进程池处理纯 Python 计算

接下来换一种任务：计算一段整数的平方和。它不主动等待外部服务，主要消耗 CPU。

请把完整代码保存为 `process_demo.py`，从终端执行 `python process_demo.py`，不要直接把进程池示例粘贴到交互解释器里：

```python
from concurrent.futures import ProcessPoolExecutor
from multiprocessing import get_context
from time import perf_counter


def sum_of_squares(limit):
    return sum(number * number for number in range(limit))


def main():
    limits = [2_000_000] * 4

    start = perf_counter()
    serial_results = [sum_of_squares(limit) for limit in limits]
    serial_time = perf_counter() - start

    start = perf_counter()
    with ProcessPoolExecutor(
        max_workers=2,
        mp_context=get_context("spawn"),
    ) as executor:
        parallel_results = list(executor.map(sum_of_squares, limits))
    parallel_time = perf_counter() - start

    print("两种方式结果一致：", serial_results == parallel_results)
    print(f"串行耗时：{serial_time:.2f} 秒")
    print(f"进程池耗时：{parallel_time:.2f} 秒")


if __name__ == "__main__":
    main()
```

这段代码显式使用 `spawn` 启动方式，让示例不依赖平台和 Python 版本的默认值。不同进程各自运行解释器，在有可用多核资源时，可以同时执行这些计算。

这里没有给出固定的“加速两倍”输出。计时包含进程启动、任务分发、结果传递和关闭的成本；任务较小时，进程池完全可能比串行更慢。可以逐步增大 `limits` 中的数值，观察计算量与调度成本的关系。

使用进程池时还要留意：

- 任务函数通常应定义在可导入模块的顶层，避免使用局部函数或 lambda 作为任务。
- 参数和返回值需要能被序列化；不能假设任意连接、锁或打开的文件都能直接传过去。
- 普通全局列表不会自动成为多个进程之间的共享列表。
- 启动进程池的流程应受 `if __name__ == "__main__"` 保护，防止子进程加载主模块时再次启动进程。

启动方式、通信机制和入口要求可参阅 [官方 `multiprocessing` 文档](https://docs.python.org/3/library/multiprocessing.html)。

## 8. GIL 不等于业务数据的锁

线程共享内存很方便，但“读取状态、判断条件、更新状态”通常是一个需要整体保护的业务操作。

例如两个线程都想领取最后一张票：如果它们都在更新之前读到了“还剩一张”，就可能重复领取。即便有 GIL，也不应该把这种多步骤业务逻辑的正确性交给解释器调度细节。

下面用锁保护完整的检查和更新过程：

```python
from concurrent.futures import ThreadPoolExecutor
from threading import Lock


class TicketCounter:
    def __init__(self, remaining):
        self.remaining = remaining
        self._lock = Lock()

    def claim(self):
        with self._lock:
            if self.remaining <= 0:
                return False
            self.remaining -= 1
            return True


def main():
    counter = TicketCounter(1)
    with ThreadPoolExecutor(max_workers=2) as executor:
        futures = [executor.submit(counter.claim) for _ in range(2)]
        results = [future.result() for future in futures]

    print("领取成功次数：", sum(results))
    print("剩余票数：", counter.remaining)


if __name__ == "__main__":
    main()
```

输出应为：

```text
领取成功次数： 1
剩余票数： 0
```

锁保护的是“检查余票并扣减”这一个完整操作。所有相关访问都要遵守同一套同步规则。它只保护当前进程内这个对象，不能直接代替多个服务器实例之间的库存协调。

协程也可能有类似问题：在读取共享状态和写回之间如果发生 `await`，其他任务可能插入执行。单线程并不意味着业务操作天然不会交错。

## 9. 一张选型表，带着前提使用

下表默认讨论启用 GIL 的常规 CPython：

| 场景 | 优先考虑 | 需要确认的条件 |
| --- | --- | --- |
| 已有同步网络或数据库代码，需要适度增加并发 | `ThreadPoolExecutor` | 客户端是否允许多线程使用、超时、连接池容量 |
| 大量网络等待，技术栈提供异步接口 | `asyncio` | 调用链是否真的非阻塞、并发数量是否受控 |
| 可拆分的纯 Python CPU 计算 | `ProcessPoolExecutor` | 计算是否足够重、数据传输成本、可用核心数 |
| 底层计算库释放 GIL 或自行并行 | 按库文档选择并实测 | 避免外层线程池与内部线程过度叠加 |
| 任务很少、开销很小 | 顺序执行 | 是否真的存在值得解决的性能问题 |

不要先把线程数调大，再希望问题自然消失。更有效的顺序是：先测量串行耗时，再识别等待和计算的比例，最后用真实数据比较吞吐量、响应时间和资源消耗。

理解并发与并行之后，你要回答的就不只是“哪个 API 更快”，而是：任务能否独立推进，等待能否重叠，计算能否拆开，以及协调这些任务要付出多少成本。
